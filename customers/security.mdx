This page is for the person who reviews this deployment for security. It describes the Deployz connector, the AWS permissions it holds, the data Deployz receives, and how to revoke access.

The install page has a **Security details** page specific to your deployment. It lists every IAM action read from the connector template you deploy, and the AWS resources your application creates. Use it for the exact permission list.

## How it works

1. You create the Deployz connector in your AWS account from a standard AWS CloudFormation template, with a Quick Create link.
2. Every minute, the connector calls Deployz over HTTPS and collects commands, such as install, update, or remove.
3. The connector applies each command with roles in your account and reports the result to Deployz.

The application, its database, its stored files, and its logs stay in your AWS account. Deployz never sees or stores your AWS credentials.

## What the connector stack creates

The connector stack, named `deployz-bootstrap-` followed by an identifier, creates:

- The connector function (AWS Lambda) and an Amazon EventBridge schedule that runs it every minute
- The connector role, with a permissions boundary and the provisioner policy
- A CloudFormation execution role for your application stack
- A permissions boundary for the IAM roles in your application stack
- An AWS Secrets Manager secret that holds the connector's Deployz credential
- Helper functions that create the installation ID and set the connector log's one-week retention

At run time, the connector also writes AWS Systems Manager parameters under `/deployz/<installation ID>/` to track unfinished commands.

The installation ID is created inside your account when the stack is created. It isn't part of the Quick Create link.

## IAM roles and permissions

The connector holds broad permissions so it can install, update, and remove the application without manual setup. Both roles below receive all their permissions when you create the connector stack, not after the connector first connects. Deployz chooses the commands and the application template that the connector applies.

Each change these roles can make is limited to this deployment, its installation scope:

- **By tag**, where AWS supports tag conditions. The resource must carry the `deployz:installation` tag with this deployment's installation ID. Creating a resource requires the request to carry that tag, and changing or deleting a resource requires the resource to carry it. A request can't add this deployment's tag to a resource that already carries another deployment's tag.
- **By name**, where AWS doesn't support tag conditions. The resource's name must start with this deployment's application stack name: `deployz-app-` followed by the first part of the installation ID, for example `deployz-app-1a2b3c4d-`.

Other Deployz deployments in the same AWS account and Region are outside this scope. A few actions can't be limited either way. See [Exceptions to installation scoping](#exceptions-to-installation-scoping).

### Connector role

The connector function runs with this role. Only AWS Lambda can assume it.

- **Permissions boundary.** A permissions boundary caps the role. The role can never exceed it.
- **Installation-scoped permissions.** Changes are limited to this deployment's resources, by tag or by name, as described above.
- **Scoped secrets access.** The role can read and update the connector's own credential secret, and the application's secrets tagged for this deployment.
- **No log reads.** The role writes the connector's own activity log. It can't read log events (`logs:GetLogEvents` and `logs:FilterLogEvents` aren't granted).
- **No network, database, or IAM role creation.** The connector role has no permission to create the network, the database, or IAM roles. It asks CloudFormation to apply the application template with the execution role below.

### CloudFormation execution role

CloudFormation uses this role to build your application stack.

- Only CloudFormation can assume it, and only on behalf of your account.
- Its changes are limited to this deployment's resources, by tag or by name, as described above.
- It can create IAM roles for your application only under the `/deployz/` path, with names that start with this deployment's application stack name, and only when each role carries the application role boundary below. The same conditions apply when it adds or attaches a policy to a role.
- The only managed policy it can attach is `AmazonECSTaskExecutionRolePolicy`.
- It has no permissions boundary of its own, because a boundary on this role wouldn't carry over to the roles it creates. The application role boundary limits those roles instead.

### Application role boundary

Every IAM role in your application stack must carry this boundary. It sets the most any of those roles can do, even if a policy grants more:

- Pull the application's container image
- Write logs to this deployment's log groups
- Read the secrets tagged for this deployment
- Use this deployment's S3 buckets and SQS queues
- Run tasks from the application's own task definitions (names starting with `DeployzApp`), only in this deployment's Amazon ECS cluster
- Pass this deployment's roles under `/deployz/` to Amazon ECS tasks

It grants no IAM management, so a role under the boundary can't create or widen other roles.

AWS can't limit which accounts a role trusts. A role in your application stack could be set up to trust another account, but it can still do only the actions above.

<Note>
  A connector stack keeps the permissions it was created with until you update it. A connector stack created before Deployz added this boundary doesn't have it. A connector stack created before Deployz added the installation scope keeps its earlier, wider permissions, where some actions reach any Deployz application in the same AWS account and Region, not only this deployment. Updating the connector stack applies the current permissions. Your software provider sends you the update steps. An application that's already installed keeps the roles it was created with and keeps working. Ask your software provider if you're not sure which applies to your deployment.
</Note>

### Resources limited by name

These resources don't support tag conditions, so their actions are limited by name to this deployment:

- **Amazon S3 buckets.** CloudFormation and the connector can change or delete only buckets whose names start with this deployment's application stack name. Before the connector deletes a bucket, it also checks the bucket's `deployz:installation` tag.
- **Log groups.** CloudFormation can set retention on, and delete, only this deployment's log groups.
- **Queues and schedules.** CloudFormation can manage only this deployment's queues and schedules. Queues and scheduled jobs are at **Preview** maturity in Deployz.
- **One-off tasks**, such as database migrations. The connector can run and stop them only in this deployment's Amazon ECS cluster.
- **Passing roles** (`iam:PassRole`). The connector and CloudFormation can pass only this deployment's roles, and only to the services that run your application: Amazon ECS, and Amazon EventBridge Scheduler for scheduled jobs. The connector can pass to CloudFormation only the execution role from its own stack.

### Exceptions to installation scoping

AWS can't limit these actions by tag or by name, so they apply to any resource of their type. Each is controlled another way:

- **Read-only actions.** Describe, list, and get calls aren't limited to this deployment. The connector uses them to observe the application, and to find this deployment's retained resources when your software provider deletes retained data. They don't change anything.
- **Removing old task-definition revisions** (`ecs:DeregisterTaskDefinition`). Amazon ECS doesn't support resource limits on this action. The connector removes only old revisions of this application's own task definitions, after a successful update. A removed revision doesn't stop a task that uses it.
- **Generating a random password** (`secretsmanager:GetRandomPassword`). A random password isn't an AWS resource. Only CloudFormation can use the role that holds this action.
- **Writing the connector's own log** (`logs:CreateLogGroup`, `logs:CreateLogStream`, and `logs:PutLogEvents`). AWS Lambda uses these actions to write the connector's activity log. They add log entries. They can't read or delete logs.
- **Creating service-linked roles** (`iam:CreateServiceLinkedRole`). This is limited to the AWS services the application uses: Amazon ECS, Elastic Load Balancing, Amazon RDS, and Amazon ElastiCache.
- **Cache parameter groups and cache nodes.** Creating, changing, or deleting the cache also uses the default parameter group and the cache nodes. The cache itself must carry this deployment's tag.

The **Security details** page for your deployment lists each of these with its resources and conditions.

## No inbound access

The connector only starts outbound HTTPS requests to Deployz. No inbound connection to your account is required, and Deployz has no path into your account. Inside the application's network, the internet-facing load balancer is the only component that accepts traffic from the internet, on ports 80 and 443.

## Application traffic

How your users' traffic reaches the load balancer depends on the address they use:

- **The default `deployz.dev` address.** Traffic passes through the Deployz Cloudflare network. HTTPS ends at Cloudflare. Cloudflare then sends the traffic over a new HTTPS connection to the load balancer in your AWS account.
- **A custom domain.** Traffic goes directly to the load balancer in your AWS account. It doesn't pass through Deployz.

If you don't want your application traffic to pass through Deployz, ask your software provider to add a custom domain, and use only that address. The default address stays available. See [Create custom domain DNS records](/customers/custom-domain-dns).

## Enrollment

The Quick Create link carries a single-use enrollment code. It ties the connector to your deployment. Deployz spends the code when the connector first connects and refuses any later attempt to use the same code with a different connector. If you select **Retry connection** on the install page, Deployz issues a new code.

## The connector's credential

The connector signs in to Deployz with a token stored in a Secrets Manager secret in your account. The token is either generated by CloudFormation in your account, or created by Deployz and passed in the Quick Create link as a hidden (`NoEcho`) parameter.

## Data Deployz receives

The connector sends Deployz operational information about the deployment:

- Installation ID, AWS account ID, and AWS Region
- Connector version, and the release and image version that runs
- Deployment state, infrastructure status, health state, and timestamps
- Resource identifiers
- AWS error messages: stack events, stopped-task reasons, and exit codes
- Health-check status code and response time (not the response body)

Configuration values and secrets that you or your software provider enter also pass through Deployz.

## Data Deployz never receives

These stay in your AWS account:

- Your application runtime and its in-memory data
- Your database data
- Your cache contents
- Your S3 data
- Your application's CloudWatch logs

Deployz doesn't automatically copy your raw application logs outside your AWS account.

Application traffic to the default `deployz.dev` address passes through the Deployz Cloudflare network, so it doesn't stay inside your AWS account. Traffic to a custom domain does. See [Application traffic](#application-traffic). Deployz doesn't ask for or store your AWS credentials.

## Secrets you enter

If the install page asks you for secret values:

- They're sent to Deployz over HTTPS and stored encrypted until your AWS account connects.
- Deployz then delivers them to AWS Secrets Manager in your account and deletes the active copy.
- If your account doesn't connect within 24 hours, the secret is deleted and must be entered again.
- Encrypted backup copies may remain for up to 7 days.
- Deployz doesn't display secret values or write them to application logs.

Values your software provider changes after your account connects stay in the update job until the connector collects it. Deployz then removes them from the job.

## Logs

Application logs are written to CloudWatch Logs in your account. The connector's own log is kept for one week.

## Revoke access

You can revoke Deployz access at any time by deleting the Deployz connector stack in your AWS account.

<Warning>
  Ask your software provider to remove the deployment and delete its retained data first. The connector stack also holds the role that CloudFormation uses for your application. After you delete the connector, Deployz can't change or remove your application, and you must remove those resources yourself.
</Warning>

**Who:** you, in your AWS console.

1. In the CloudFormation console, in the application's Region, select the connector stack (its name starts with `deployz-bootstrap-`).
2. Delete the stack. This deletes the connector function, its schedule, and its roles.

The connector stops. Because Deployz has no inbound path into your account, it can't reconnect. Deployz shows the connector as disconnected when it stops receiving check-ins.

For the full removal order, see [Remove the application](/customers/remove).
