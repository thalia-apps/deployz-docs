A release is one version of your application: a container image that Deployz builds from one commit, with a version label you choose. A release never changes after it's built, so every customer who runs version `v1.3.0` runs the same container image.

Creating a release doesn't update any customer. Running deployments keep their current release until you [deploy an update](/operate/deploy-update). New installs get your newest release that built successfully.

## Before you start

- Every required build variable has a value. If one is missing, you can't create a release. See [Configure environment variables](/prepare/environment-variables).
- Your application fits the [application requirements](/prepare/requirements). Deployz doesn't check the analysis result before it builds, so a release can build even when the analysis still lists required changes. Those changes still block new deployments.

## Create the release

**Who:** you (the vendor), in the Deployz dashboard.

<Steps>
  <Step title="Open the Releases tab">
    Open your application and select **Releases**.
  </Step>
  <Step title="Open the form">
    Select **Create release**. The **New release** form opens.
  </Step>
  <Step title="Enter a version">
    In **Version**, enter a label such as `v1.3.0`. Deployz suggests the next patch version after your newest release, or `v0.1.0` for the first one. When your newest release's version isn't in the `1.2.3` or `v1.2.3` form, the field starts empty. Each version must be unique for the application, including versions whose build failed. If you reuse a version, the form shows "Couldn't create this release. Try again."
  </Step>
  <Step title="Choose the commit">
    In **Commit**, select a commit from the list. The list shows commits from your application's branch. To use another commit, select **Enter commit SHA manually** and paste its SHA, from 7 to 40 characters. Deployz checks the SHA with GitHub. If the commit isn't in the repository, the form shows "This commit doesn't exist in the repository." If GitHub is unavailable, enter the full 40-character SHA.
  </Step>
  <Step title="Create it">
    Select **Create release**. Deployz starts building the container image. A build usually takes a few minutes, and the page updates when it finishes.
  </Step>
</Steps>

If the commit has been released before, the form shows **Already released as** with the earlier versions.

If a required build value is missing, the form shows "Set these build values before you build a release:" with the variable names. Select **Review configuration**, enter the values, then create the release again.

### Build the first release from the test deployment page

**Who:** you (the vendor), in the Deployz dashboard.

If your application has no built release when you create a test deployment, the page offers **Build release from commit** followed by a short SHA. This builds the commit the analysis read. The release's version is the first 12 characters of that commit's SHA, for example `a1b2c3d4e5f6`. Because that version isn't in the `v1.2.3` form, the **Version** field starts empty the next time you create a release. Enter a version of your choice.

## Build limits

- **Timeout.** A build that runs longer than 60 minutes stops and shows **Build failed** with "The version build ran out of time."
- **Architecture.** Deployz builds every container image for Linux on x86_64 (`linux/amd64`). For how Deployz runs `docker build`, see [How Deployz builds the container image](/prepare/requirements#how-deployz-builds-the-container-image).
- **Registry rate limits.** When the container registry limits base image downloads, Deployz retries the build on its own, up to 3 times, after waiting 1, 3, and 8 minutes. If the limit continues, the build fails. See [Fix a failed build](/releases/build-failures).

## Build statuses

The **Build** column on the **Releases** tab shows each release's status:

| Status | Meaning | What you can do |
| --- | --- | --- |
| **Building** | Deployz is building this release from its commit. | Wait. New installs keep using your newest **Ready** release. If none exists yet, customers can't install until the build finishes. |
| **Ready** | The build finished successfully. | Deploy it, or let new installs use it. |
| **Build failed** | The build stopped before it produced a container image. | See [Fix a failed build](/releases/build-failures). |
| **Unavailable** | The release's container image no longer exists, so it can't be deployed. | Create a new release from the same commit to deploy that code again. |

The newest **Ready** release has a **Customer installs** label. That's the release new customer installs get. The line above the table names it, for example "Customer installs get v1.3.0 (commit a1b2c3d)."

To see a release's full commit SHA and creation time, select the arrow next to its version. **Running on** shows which deployments currently run each release.

## Check for infrastructure changes

When your application has at least one deployment, the **Releases** tab compares what your application needs now with what one of its deployments was created with. It checks only one of the application's deployments, not every deployment:

- **No infrastructure changes** means that deployment has the same parts your application needs now.
- **Infrastructure requirements changed** means the parts differ. The notice reads: "This release needs infrastructure changes. Deployz cannot apply them to an existing deployment. Create a new deployment for each customer that needs this release."

The notice is a summary. The check that runs when you deploy a release to a deployment decides whether the deploy can go ahead:

- **Deployz refuses the deploy** when the application now needs a database or cache that the deployment doesn't have, a different database engine, or a different set of workers, queues (**Preview**), or scheduled jobs (**Preview**). The message names what's missing, for example "The application now needs a database, which this deployment does not have."
- **Deployz allows the deploy** when the application no longer needs a database or cache that the deployment has. The notice still shows **Infrastructure requirements changed** in this case. The unused database or cache stays in the deployment.

Deployz doesn't change what an existing deployment contains. To give a customer the new requirements, create a new deployment for them. See [Changing what a deployment contains](/prepare/not-supported#changing-what-a-deployment-contains).
