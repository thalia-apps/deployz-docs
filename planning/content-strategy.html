1. Where we are today

The product is well understood internally, but almost nothing is written for users yet.

Gap

The docs site is an empty starter

It has two placeholder pages. The header links point to Mintlify's own docs and blog, and the Changelog link goes to a page that doesn't exist.

Strength

Strong internal source material

The app repository has about 8,400 lines of engineering docs, checked against the code. They're written for engineers, so we use them as raw input, not as finished copy.

Opportunity

The app doesn't link to any docs

The Contact Deployz support button has no destination. Linking error screens to the docs would bring readers in at the moment they need help.

Scope

No API reference needed

Deployz has no public API: no API keys and no API spec. The dashboard's own routes are internal, so we don't document them.

2. The product in one picture

Deployz lets a software company (the vendor) run its web application inside each of its customers' own AWS accounts.

Step 1Connect a GitHub repository
Vendor
Step 2Deployz analyzes it and builds a release
Deployz
Step 3Vendor sends an install link
Vendor
Step 4Customer reviews the plan and cost, then approves one AWS stack
Customer
Step 5Vendor runs every deployment from one dashboard
Vendor

Three things about the product shape the docs:

It's opinionated

It supports one application shape. Anything else is rejected with an explanation. So the docs must answer "does my app fit?" early and clearly.

Two people act, only one has an account

The vendor uses the dashboard. The customer never signs in and works only on the install page and in their AWS console. Every task must say who does it.

It runs in someone else's AWS account

Many install problems come from the customer's AWS settings. Vendors need pages they can forward to their customer's IT or security team.

3. Who reads the docs

Primary

Vendor: evaluator

A founder or lead developer at a 5–20 person SaaS company. Knows Docker, may not know AWS well.

Needs: does my app fit, what will it cost, and the fastest path to a working test.

Primary

Vendor: operator

The same person after going live, or a teammate.

Needs: deploy, roll back, change settings, add domains, remove deployments, fix failures.

Secondary

Vendor team member

Someone invited to the organization as an admin or member.

Needs: what their role can do, and how to get started.

Secondary, but critical

Customer: approver

The IT, cloud or security person at the vendor's customer who approves the AWS stack.

Needs: what's created, what access Deployz has, what it costs, and how to revoke it and remove it.

Not for the public site: Deployz's own internal operations (the support console, how Deployz deploys itself, CI, configuration settings, test tools). That stays in the app repository.

7. Writing rules for Deployz pages

Say who acts

Start every task with a "Who" line: the vendor in the dashboard, or the customer in their AWS console.

Lead with fit

Say plainly what isn't supported. "We don't support that" beats "it might work".

Product words, not AWS jargon

Use AWS service names only where the reader needs them, mainly in the customer guide.

Warn before the action

Rollback doesn't undo database changes. Removal keeps data that still costs money. Region and size can't be changed later.

Mark Preview features

Queues and scheduled jobs carry a Preview label until they're proven on real AWS.

Public before launch

Publish prices and limits as they are now. Don't promise roadmap features or dates.

10. Why the customer security page needs a review before each release

This is the page a customer's security team reads before allowing Deployz into their AWS account. It makes specific promises, and those promises depend on code that changes.

What the page promises

  • Deployz's access is limited to resources it tags for that installation.
  • Deployz never connects into the account. The connector only reaches out.
  • Deployz receives IDs, states, AWS error text and health-check codes, never the app's responses or logs.
  • Secrets are deleted after 24 hours if the account never connects, and backups last up to 7 days.
  • Deleting the connector stack revokes all access.

Why it can quietly become false

  • These facts live in several places: the AWS permissions template, the connector code, the secrets code and the page text.
  • A new feature can add permissions. Queues and schedules already did.
  • Nothing currently forces the page text to be updated when that code changes.
  • One internal doc already contradicts itself about where secrets appear.
Why it matters: customers copy these answers into their own security reviews. If a release changes Deployz's access and the page isn't updated, a customer approved something different from what they were told. That's a trust and contract risk, not just a typo.
Decided

An AI coding agent does the check

WhenEvery app pull request that touches the permissions template, connector, secrets or security-page files, and once before each release
WhatChecks each security promise against the code, using a fixed list of promises and their source files
ResultA pull request comment marking each promise still true, changed or can't verify, with file evidence and suggested wording
GateA changed promise blocks the release until the docs and the in-app page are updated

Each security page also records the app commit it was last checked against.
