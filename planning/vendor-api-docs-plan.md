# Vendor API documentation plan

Status: proposal, 2026-11-24. Checked against deployz `626521a3` (production web `8f612be8`, api `3b943428`).
Goal: publish vendor API documentation, then switch the API on (`PUBLIC_API_ENABLED=true`).

## 1. What exists today

| Source | What it gives us |
| --- | --- |
| `apps/api/openapi.json` (OpenAPI 3.1, generated by `pnpm --filter @deployz/api openapi`) | 12 operations: applications, releases, deployments, jobs, plus the spec itself. Has `servers` (`https://api.deployz.dev`), bearer auth, an envelope schema on every response, and descriptions on the write routes. No tags, no examples. Summaries say "installation". |
| `docs/vendor-api.md` (internal) | Authentication, key rules, the creator rule, idempotency, polling, errors, rate limits, a GitHub Actions example. |
| **Settings › API keys** (`apps/web/src/app/dashboard/settings/api-keys/`) | Create (Name, Permission Read/Deploy, Expires after 30/90/365 days), copy once, list with status, revoke. Visible in production today. |
| Account routes under `/api/v1` (`MIRRORED_ROUTES`) | About 35 more routes: organization, team, API keys, applications, environment variables, customers, invitations, create/update/remove/purge deployments, deprecate release. **Not in the OpenAPI document.** |

Production check: `https://api.deployz.dev/api/v1/*` answers `404 PUBLIC_API_DISABLED`.

## 2. Scope

**Recommended for launch: the 11 pipeline operations in `openapi.json`.** They are the contract the spec, the tests (`public-api-v1.test.ts`, `e2e/scenario-vendor-api.spec.ts`) and the response allowlist (`public-api-views.ts`) cover. This matches "use the OpenAPI Specification as the source".

**Not at launch: the account routes.** They aren't in the spec, their responses don't go through the allowlist, and they mirror dashboard handlers. If they should be public, add them to `public-api-spec.ts` first, then document them in a second phase. Until then, the docs say the API covers the pipeline only, and the account routes aren't a supported contract.

Not documented in any phase: billing, GitHub, ownership transfer, account deletion, bulk deploy, Reconnect AWS (all answer 404 under `/api/v1`), and the dashboard routes under `/api/...`.

## 3. Changes in the app repository first (source of truth)

Small, generated-spec changes in `apps/api/src/public-api-spec.ts`, then regenerate `openapi.json`:

1. **Terminology:** "installation" → "deployment" in summaries and descriptions (`listDeployments`, `getDeployment`, `deployRelease`).
2. **Tags:** `Applications`, `Releases`, `Deployments`, `Operations` on each operation, so Mintlify groups the sidebar.
3. **Examples:** one response example per operation and request examples for `createRelease`, `deployRelease`, `rollbackDeployment`. Mintlify shows them, and they make the code samples realistic.
4. **Exclude the spec route from the docs:** `x-excluded: true` on `getOpenApiDocument` (or an overlay, see 4.2).
5. **Error codes per operation:** list the `409` codes in each response description (`RELEASE_VERSION_EXISTS`, `RELEASE_BUILD_IN_PROGRESS`, `DEPLOYMENT_BUSY`, `IDEMPOTENCY_KEY_REUSED`, `RELEASE_DEPRECATED`, `RELEASE_NOT_READY`).
6. **In-app link:** on **Settings › API keys**, point "OpenAPI document" (or add a link) to the docs page `https://deployz.dev/docs/api/overview`.

`public-api-spec.test.ts` keeps the committed file equal to the generated one.

## 4. Mintlify setup in this repository

### 4.1 Spec source

Commit a copy as `api-reference/openapi.json`, synced from the app repo by a script (`scripts/sync-openapi.mjs`) that copies `apps/api/openapi.json` at a given commit and records the commit in the PR.

Don't point Mintlify at `https://api.deployz.dev/api/v1/openapi.json`. It answers 404 while the API is off, which breaks the build, and a hosted spec doesn't redeploy the docs when it changes.

### 4.2 Overlay for docs-only changes

`api-reference/overlay.yaml` (OpenAPI Overlay 1.0) for anything that belongs only on the docs site: `x-mint.content` notes such as "Needs a Deploy key", and `x-excluded` if the app spec doesn't set it. Keep wording fixes in the app spec, not the overlay.

### 4.3 Navigation and settings (`docs.json`)

New tab **API reference** after **Customer guide**:

```
API reference
  Get started
    api/overview          Overview: what the API does, base URL, envelope, versioning
    api/authentication    API keys: create, permissions, expiry, creator rule, revoke
    api/pipeline          Build and deploy from your pipeline (GitHub Actions)
    api/errors            Errors and rate limits
  Endpoints               (generated from api-reference/openapi.json)
    Applications          GET /api/v1/applications, GET /api/v1/applications/{id}
    Releases              list, read, create
    Deployments           list, read, deploy, restart, rollback
    Operations            GET /api/v1/deployments/{id}/jobs/{jobId}
```

`api` settings:

```json
"api": {
  "playground": { "display": "simple" },
  "examples": { "languages": ["bash", "javascript", "python"], "defaults": "required" }
}
```

**Playground: `simple`, not `interactive`.** Interactive mode would send a reader's deploy-capable key through Mintlify's proxy and run real deploys from the docs. Simple mode shows the request and code samples without sending.

## 7. Verification

2. On staging, with `PUBLIC_API_ENABLED=true`: create a Read key and a Deploy key, run every documented request and the GitHub Actions example as written, and check one example of each error code (`401`, `403`, `404`, `409`, `429`).

4. Mintlify preview of the branch: generated pages, grouping, code samples, mobile layout.

## 8. Launch sequence

1. App PR: spec improvements (section 3). Merge and deploy to production. The API is still off.
2. Docs PR on a branch: spec copy, overlay, pages, navigation, AGENTS.md. Review in the Mintlify preview. Keep it unmerged.
3. Staging run-through (section 7.2). Fix the docs.
4. Launch: merge the docs PR, confirm the docs are live, then set `PUBLIC_API_ENABLED=true` and redeploy the API. Check `GET https://api.deployz.dev/api/v1/openapi.json` answers 200 and one keyed `GET /api/v1/applications` works.
5. Same day: marketing PR and deploy, and the changelog entry.

If the API launch slips after the docs merge, the pages say the API isn't available yet, or the tab stays out of `docs.json` until launch.

## 9. Decisions needed

1. **Scope:** pipeline operations only at launch (recommended), or add the account routes to the spec first and document them too.
2. **Playground:** `simple` (recommended) or `interactive`.
