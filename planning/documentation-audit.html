Deployz docs audit

We read every page of the Deployz docs and compared what each one says with what the product actually does. This page lists everything that's wrong, missing or unclear, starting with what matters most.

What already works

  • No broken links: all 278 internal links and 37 anchors resolve (mint broken-links and mint validate both pass).
  • Every one of the 25 failure codes in the product has its own section in the docs.
  • No banned words (simply, just, easy, obviously) and no British spellings.
  • Every page has a title and description, and headings are in the right order.
  • Most button names, status labels and on-screen text match the product exactly.
  • The product doesn't link to the docs anywhere yet, and Contact Deployz support isn't a link.

The big picture

Most problems fall into five groups.

Security

The customer security page says Deployz's AWS permissions are limited to one deployment. Several actually reach the whole AWS account, and the page doesn't say that web traffic to the default address goes through Deployz's Cloudflare service.

Wrong steps

Some pages describe behavior the product doesn't have, such as migrations being skipped on retry, or setting changes reaching existing deployments. A reader who follows them gets surprised.

Dead ends

Some instructions point to buttons that don't exist in that situation, like "deploy again" after a failed first install, or "revoke" for an invitation.

Missing pieces

Real behavior isn't documented anywhere: install links that expire after 30 days, billing that continues while a deployment is broken, team roles, and the variables Deployz sets for you.

Tidiness

Tables are copied across pages and have started to differ. The troubleshooting hub is missing 11 problems, the glossary is missing many terms, and Preview labels are used inconsistently.

Fix these first

These 16 issues could lead a reader to do the wrong thing, or misstate security or billing. Items marked “needs a decision” can't be fixed in the docs until someone decides how the product should behave.

Things to fix in the product itself

We found these while checking the docs, but they're product problems. Several docs fixes depend on them.

  1. After a failed first install, some failures leave the vendor with no button to try again.
  2. A deployment's install link expires after 30 days, and there's no way to extend it from the dashboard.
  3. There's no way to revoke an invitation from the dashboard.
  4. Some product text contradicts the buttons, for example “run the install link again” and “a new link invalidates the old one”. On customer pages, “Vendor recommended” should say “your software provider”.
  5. Security questions: whether to tell customers about the Cloudflare proxy, whether several deployments can share one AWS account and Region, and whether the permissions that reach the whole account should be narrowed.
  6. Some statuses and failure codes are never shown: Disconnected, Applying configuration, and three failure codes.
  7. The “Infrastructure requirements changed” warning can appear when nothing is blocked.
  8. After a failed configuration update, the new secret values stay in AWS.
  9. A deployment the customer never installed can't be removed from the dashboard.
  10. The cost estimate always includes a load balancer, even when none is created.
  11. The product tells vendors to set a start command in Deployz, but there's no field for it.
  12. Any team member can manage billing, remove deployments and add domains. Is that intended?
  13. Repeat installs from the same email address create duplicate customer records.

Questions for the product owner

  1. What should a vendor do after a failed first install that has no retry button?
  2. Which AWS Regions can customers actually install in today? The docs claim 17, but the code defaults to one.
  3. Should the security page mention the Cloudflare proxy, and list every permission that reaches the whole account?
  4. Should the docs keep the Revoked invitation status until a revoke button exists?
  5. Is the 30-day expiry of a deployment's own install link intended?
  6. Should any team member be able to manage billing and remove deployments?
  7. Can the docs use “container image” and “build” as nouns when talking about Docker?
  8. Should repeated tables, such as costs and Regions, become shared snippets?
  9. Should the changelog list changes made before launch?
  10. How long does Deployz keep a customer's data and secrets after a deployment is removed?

Suggested order of work

  1. Security and billing: fix the security page, the billing page and the quickstart subscription note, and hide AGENTS.md from the public site.
  2. Wrong instructions we can fix now: migrations, build variables, setting changes, connector links, custom domain timeouts and configuration scope.
  3. After product decisions: first-install recovery, invitation revoking, link expiry and Regions.
  4. Troubleshooting and glossary: add the 11 missing hub rows and the missing failure headings, and fill in the glossary.
  5. New pages: the team page first, then the analysis and fix-findings pages, then limits.
  6. Polish: remove duplicate tables, use consistent Preview labels, add “who does this” lines, start the changelog, and clean up starter files.
