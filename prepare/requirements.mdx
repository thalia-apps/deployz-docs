Deployz supports one application architecture and runs it the same way in every customer's AWS account. Check your application against this page before you add it. If something you rely on isn't listed here, read [What Deployz doesn't support](/prepare/not-supported).

When you add an application, Deployz analyzes the repository and reports anything that doesn't fit. You don't need to declare most of the items below by hand. The analysis result on the application's **Overview** tells you whether the application fits as it is, fits after you change your repository, or needs something Deployz doesn't provide. See [Read the analysis result](/prepare/analysis#read-the-analysis-result).

## What each deployment contains

One deployment is one copy of your application in one AWS Region of one customer's account. It contains:

| Part | What Deployz runs | Needed? |
| --- | --- | --- |
| Web service | Your container, behind a load balancer, with a permanent HTTPS URL | Always |
| Background workers | One extra container per declared worker process, with no URL | Optional |
| Database | Managed PostgreSQL 16 or MySQL 8.0 (Amazon RDS) | Optional |
| Cache | Managed Valkey, which is Redis-compatible (Amazon ElastiCache) | Optional |
| File storage | One S3 bucket | Always created |
| Queues (**Preview**) | One or more SQS Standard queues, each with an optional dead-letter queue | Optional |
| Scheduled jobs (**Preview**) | One or more one-shot tasks that run on a schedule | Optional |
| Network | A dedicated network (VPC) for this deployment | Always |

Deployz adds the optional parts only when the analysis finds that your application needs them. For the full list of AWS resources, see [AWS resources Deployz creates](/reference/aws-resources).

<Note>
  Queues and scheduled jobs are at **Preview** maturity. They haven't been qualified on real AWS accounts.
</Note>

## Container image

- **A Dockerfile in the repository.** Deployz builds your application from a Dockerfile that produces a production container image. A Dockerfile that's only for development, is a template, copies files the repository doesn't contain, or copies nothing from the repository doesn't count. The build can't use the `.git` directory, because Deployz builds from a source archive that doesn't include it.
- **One container image per release.** The web service, every worker, the migration task, and scheduled jobs all run the same container image with different commands. A worker that needs its own Dockerfile isn't supported.
- **A start command in the repository.** The Dockerfile needs a `CMD` or `ENTRYPOINT`, or the repository needs a `start` script in `package.json`. The Deployz dashboard has no field for the start command, so set it in your repository.
- **Linux on x86_64.** Deployz builds and runs containers on Linux with the x86_64 CPU architecture (`linux/amd64`). Containers run on AWS Fargate.

### How Deployz builds the container image

Deployz builds the container image when you [create a release](/releases/create):

- It runs `docker build` with the Dockerfile the analysis selected.
- The build context is the Dockerfile's own directory. For example, `COPY requirements.txt .` in `backend/Dockerfile` copies `backend/requirements.txt`. When the analysis finds that a Dockerfile is meant to be built from the repository root, such as one in a `docker/` folder, Deployz uses the root instead.
- A multi-stage Dockerfile builds its last stage. If the last stage is a tooling stage rather than the application, Deployz builds the application stage the analysis found.
- Build values you configure reach the build as build arguments. See [Build or runtime](/prepare/environment-variables#build-or-runtime).

For build limits, such as the timeout, see [Create a release](/releases/create#build-limits).

## Web service

Your web service must:

- **Listen on one port.** Deployz sends customer traffic and health checks to a single container port. The analysis looks for it in the Dockerfile (`EXPOSE` or `ENV PORT`), env files, Compose files, and code defaults. If it can't find one, set it on the **Configuration** tab.
- **Listen on all network interfaces.** A server that binds only to `127.0.0.1` or `localhost` never receives traffic. Bind to `0.0.0.0`.
- **Answer a health check.** The load balancer requests a health check path on your port. Deployz doesn't treat a deployment as healthy, or send traffic to a new release, until this check passes.
- **Keep no state on local disk.** The container's disk is wiped on every deploy and restart. Store uploaded and generated files in the S3 bucket, and data in the database.

### Health check path

The analysis chooses the health check path. You can change it on the **Health check** row in **Configuration** › **Resources**.

| What the analysis finds | Path Deployz checks | Responses that pass |
| --- | --- | --- |
| A health route or a Dockerfile `HEALTHCHECK` that names a path, such as `/health` | That path | HTTP `200` |
| No health route | `/` | Any HTTP `200`–`399` response, so a redirect to a login or setup page passes |
| A health handler file whose route it can't resolve | None until you enter one. The analysis asks you for the path. | HTTP `200` |

A path you enter yourself must return HTTP `200`. If your application checks the `Host` header, it might answer the load balancer's request with HTTP `400`. When the analysis detects this, Deployz also accepts `400`, because the response still proves the process is up.

A changed port or health check path applies to new deployments only. Existing deployments keep the values they were created with.

## Background workers

A worker is a long-running process, such as a job runner, that runs next to the web service. Deployz runs one container for each worker that your repository declares, for example a non-web process in a `Procfile` or a worker service in a production Compose file.

- Each worker runs from the same container image as the web service, with its own start command.
- Each worker runs one task. Workers have no URL and receive no traffic from the load balancer.
- If the analysis finds code that looks like background jobs but no command that starts a separate job runner, it shows a recommended finding. If the web process already runs the jobs, you don't need to change anything. Otherwise, declare the job runner with its own start command in your repository, for example a worker line in a `Procfile`.

For how Deployz detects workers, queues, and schedules, see [Workers, queues, and scheduled jobs](/prepare/workers-queues-schedules).

## Data services

- **Database.** PostgreSQL 16 or MySQL 8.0. Deployz provisions it, connects your application to it, and keeps automated backups for 7 days. If your application has a migration command, see [Database migrations](/prepare/migrations).
- **Cache.** A single-node Valkey cache that's compatible with standard Redis clients. It has no TLS and no cluster mode.
- **File storage.** One S3 bucket, created for every deployment. Your application gets its credentials from AWS automatically, so it doesn't need access keys.

Deployz passes connection details to your application through environment variables. For the names, see [Variables Deployz sets](/prepare/data-services#variables-deployz-sets).

<Warning>
  When you remove a deployment, the database, its credentials, and the S3 bucket stay in the customer's AWS account and keep costing money until their data is deleted. Queues are deleted, together with any messages still in them. See [Remove a deployment](/operate/remove).
</Warning>

## Queues and scheduled jobs (Preview)

- **Queues** (**Preview**). Deployz provisions an SQS Standard queue only when the analysis finds clear evidence that your application both sends messages to it and receives them. Weaker evidence becomes a question for you. The analysis reads only JavaScript and TypeScript code for queues. SQS use in Python code becomes a question and never creates a queue. You can't declare a queue by hand.
- **Scheduled jobs** (**Preview**). Deployz provisions a scheduled job only from a `render.yaml` service with `type: cron`, or a Kubernetes `CronJob` manifest, that names both a schedule and a command. The job runs your release's container image as a one-shot task.

For details, see [Workers, queues, and scheduled jobs](/prepare/workers-queues-schedules).

## Sizes

Every deployment uses one of three fixed size presets. The size sets capacity only, never which parts the deployment contains.

| Size | Each task (web and each worker) |
| --- | --- |
| Small | 0.25 vCPU, 512 MiB memory |
| Medium | 1 vCPU, 2 GiB memory |
| Large | 2 vCPU, 4 GiB memory |

You set a **Default size** and a **Minimum allowed size** for the application. The customer chooses a size before they install. A deployment's size and Region can't be changed after it's created. For database and cache sizes and estimated AWS costs, see [Sizes and AWS cost](/share/sizes-and-cost).

## Runtimes

Deployz runs whatever your Dockerfile builds. The analysis recognizes Node.js, Python, Ruby, Go, JVM languages, .NET, PHP, Elixir, and Rust projects, which helps it find your port, start command, and dependencies. Recognition doesn't mean a framework has been tested with Deployz.
