---
title: "What Deployz doesn't support"
description: "Application patterns and platform features Deployz rejects or doesn't provide, and what to do instead."
---

Deployz supports one architecture, described in [Application requirements](/prepare/requirements). This page lists what falls outside it, so you can decide early whether Deployz fits your application.

There are two kinds of limits:

- **Blocking analysis findings.** The analysis found something in your repository that Deployz can't run. Deployz won't deploy the application until you change the repository.
- **Platform limits.** Things Deployz doesn't provide for any application, whatever your repository contains.

## Blocking analysis findings

When the analysis finds one of these, the application needs changes before Deployz can deploy it. Each finding shows the file or dependency it found as evidence.

To resolve a blocking finding, change the repository, push the change to the application's branch, then open the **More actions** menu at the top of the application and select **Re-analyze application**. Files in documentation, example, and test folders don't count as evidence. For help with a specific finding, see [Fix analysis problems](/troubleshooting/analysis).

### Databases and search engines

Deployz hosts PostgreSQL 16 and MySQL 8.0 only.

| Detected | What to do instead |
| --- | --- |
| MariaDB driver or configuration | Move to MySQL or PostgreSQL, or remove the dependency if it isn't used. |
| MongoDB | Move the data layer to PostgreSQL or MySQL, or remove the dependency if it isn't used. |
| SQLite, as the production database | Move to PostgreSQL or MySQL. If your application supports several engines, configure it to use one of those. |
| Elasticsearch or OpenSearch | Use PostgreSQL full-text search, or remove the dependency if it isn't used. |
| Other databases, such as Cassandra, Neo4j, ClickHouse, or an embedded JVM database like H2 | Move to PostgreSQL or MySQL. |
| A PostgreSQL image that provides an extension Amazon RDS doesn't offer | Remove the dependency on that extension. |

If your application includes a driver for an unsupported engine and also a PostgreSQL driver, the analysis treats the engine as a configuration choice and doesn't block it.

### Redis features

Deployz provides a standard, single-node Valkey cache that's compatible with Redis clients. It blocks applications that require:

- Redis Stack modules, such as RedisJSON or RediSearch
- Redis Cluster mode
- TLS connections (`rediss://`)

Use a standard single-node Redis setup without these features.

### Message brokers and workflow engines

- **Kafka**, **RabbitMQ**, and a **Temporal** server aren't hosted. If the application can use a queue Deployz provides, Redis or an SQS Standard queue (Preview), switch to it. Otherwise Deployz doesn't fit this application.
- **SQS FIFO queues** aren't supported. Only SQS Standard queues are, and they're at Preview maturity.

### Infrastructure your repository manages itself

Deployz creates and owns the infrastructure for every deployment, so it can't run next to infrastructure code your application relies on:

- Kubernetes manifests, Helm charts, or kustomize files for the application itself
- Serverless Framework or AWS SAM configuration
- Your own Terraform, Pulumi, or CloudFormation templates
- Azure or Google Cloud deployment files

Keep these files if self-hosters use them. Deployz ignores them when they're in a deployment or sample folder, such as `deploy/`, `helm/`, `k8s/`, or `infra/`, and shows a warning instead of blocking.

### Container setup

| Detected | What to do instead |
| --- | --- |
| No Dockerfile that builds a production image | Add a production Dockerfile that builds and starts the application from source. |
| A production Compose file with more than one application service | Run the application as one web service. Declare other long-running processes as workers. |
| An image that runs several processes under a supervisor, such as s6-overlay or supervisord | Build an image that runs only the web process, and declare each other process as a worker. |
| A GPU requirement | Use a CPU-only configuration, or move the GPU work to a service that provides it. |

### Local storage

The container's disk is wiped on every deploy and restart.

| Detected | What to do instead |
| --- | --- |
| A persistent volume: a Kubernetes volume claim, a Terraform-managed volume, or named volumes in a production Compose file | Store persistent data in the S3 bucket or the database. |
| A durable data directory with no `VOLUME` or Compose mount | Store the data in the S3 bucket or the database. |
| A configuration file the image expects to be mounted, which no Dockerfile instruction creates | Create the file in the Dockerfile, or read the settings from environment variables. |
| Files written to the local disk | Store files in object storage. Deployz provides an S3 bucket for every deployment. |

## Platform limits

These apply to every application.

### Networking and accounts

- **Existing VPCs or databases.** Each deployment creates its own network and data services. It can't join an existing VPC or use an existing database.
- **Private connectivity.** PrivateLink, AWS Direct Connect, VPN connections, and private-only applications with no public endpoint aren't supported.
- **Custom networking.** Custom proxies, custom DNS architectures, and custom IAM aren't supported. To use your own domain, see [Add a custom domain](/operate/custom-domains).
- **Restrictive AWS accounts.** An account whose service control policies (SCPs) block the standard stack can't install. See [Before you install](/customers/before-you-install).
- **Other clouds and locations.** Deployz deploys only to AWS. On-premises and air-gapped environments aren't supported.

### Regions

- **One Region per deployment.** Multi-Region and active-active deployments aren't supported.
- **The Region is fixed.** You can't move a deployment to another Region. To use a different Region, create a new deployment. See [AWS Regions](/share/regions).

### Capacity

- **No resizing.** You can't change a deployment's size after it's created. To use a different size, create a new deployment.
- **No autoscaling.** Each web service and each worker runs one task, with the capacity of the chosen size preset. Custom AWS sizing isn't available.

See [Sizes and AWS cost](/share/sizes-and-cost).

### Changing what a deployment contains

A deployment keeps the parts it was created with. If your application later needs a database or cache the deployment doesn't have, a different database engine, or a different set of workers, queues, or scheduled jobs, Deployz refuses to deploy the new release to that deployment. To deliver it, create a new deployment for that customer, or change the application's requirements back.

These changes don't need a new deployment: dropping a database or cache the application no longer uses, and changes to the runtime, port, health check path, environment variable values, or migration command.

### Builds

- **One image for all customers.** Deployz builds one image per release. Per-customer builds and values that a customer enters at build time aren't supported. See [Configure environment variables](/prepare/environment-variables).

### Features Deployz doesn't provide

- Deployment notifications by email or Slack, and webhooks
- Release approval workflows and scheduled releases
- Backup management beyond the database's automated backups
- Run history for scheduled jobs
- Application logs and monitoring in Deployz. Runtime logs stay in the customer's AWS account, and Deployz never copies them out.
- Actions for customers inside Deployz. Customers approve the install in their AWS console and have no Deployz account.
