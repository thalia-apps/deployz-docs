Deployz supports one architecture, described in [Application requirements](/prepare/requirements). This page lists what falls outside it, so you can decide early whether Deployz fits your application.

There are three kinds of limits:

- **Capabilities Deployz doesn't provide.** Your application needs something Deployz can't run, such as MongoDB or a GPU. The **Overview** shows **Not deployable on Deployz**, and the item is listed under **Not supported**.
- **Patterns that need a repository change.** Deployz can't run the repository as it is, but a known change fixes it, such as removing a `.git` copy from the Dockerfile or moving files from the local disk to S3. The **Overview** shows **Deployable after repository changes**, and the item is listed under **Change in your repository**.
- **Platform limits.** Things Deployz doesn't provide for any application, whatever your repository contains.

Deployz won't deploy the application until you resolve every required item, including repository changes. If you know the application doesn't use a blocking database, Redis, broker, volume, or local-file item in production, you can [mark it as not used in production](/prepare/analysis#mark-a-blocker-as-not-used-in-production). GPU, infrastructure your repository manages itself, a missing Dockerfile, and a `.git` copy can't be marked. Each item shows the file or dependency it found as evidence. Files in documentation, example, and test folders don't count as evidence.

## Resolve an item in your repository

**Who:** you (the vendor), in your repository and the Deployz dashboard.

1. Change the repository, and push the change to the application's branch.
2. Open the **More actions** menu at the top of the application, then select **Re-analyze application**.

For instructions you can follow yourself or give to a coding agent, see [Fix analysis findings](/prepare/fix-findings). For help with a specific item, see [Fix analysis problems](/troubleshooting/analysis).

## Capabilities that Deployz does not provide

Each capability below is listed under **Not supported**, with one exception: SQLite. When your application also has a PostgreSQL or MySQL driver, the analysis lists SQLite under **Change in your repository** instead, because you can configure the application to use that engine.

### Databases and search engines

Deployz hosts PostgreSQL 16 and MySQL 8.0 only.

| Detected | What to do instead |
| --- | --- |
| MongoDB | Move the data layer to PostgreSQL or MySQL, or remove the dependency if it isn't used. |
| SQLite, as the only database driver | Move to PostgreSQL or MySQL. |
| Elasticsearch or OpenSearch | Use PostgreSQL full-text search, or remove the dependency if it isn't used. |
| Other databases, such as Cassandra, Neo4j, or ClickHouse | Move to PostgreSQL or MySQL. |
| An embedded JVM database, such as H2, HSQLDB, or Apache Derby, with no PostgreSQL or MySQL driver | Move to PostgreSQL or MySQL. |
| A PostgreSQL image in a production Compose file that provides an extension Amazon RDS doesn't offer, such as ParadeDB, TimescaleDB, or Citus | Remove the dependency on that extension. |

MariaDB is a repository change, not a capability gap. See [Databases](#databases).

### Redis features

Deployz provides a standard, single-node Valkey cache that's compatible with Redis clients. It can't run applications that require:

- Redis Stack modules, such as RedisJSON or RediSearch
- Redis Cluster mode
- TLS connections (`rediss://`)

Use a standard single-node Redis setup without these features.

### Message brokers and workflow engines

- **Kafka**, **RabbitMQ**, and a **Temporal** server aren't hosted. If the application can use a queue Deployz provides, Redis or an SQS Standard queue (**Preview**), switch to it. Otherwise Deployz doesn't fit this application.
- **SQS FIFO queues** aren't supported. Only SQS Standard queues are, and they're at Preview maturity.

### Infrastructure your repository manages itself

Deployz creates and owns the infrastructure for every deployment, so it can't run next to infrastructure code your application relies on:

- Kubernetes manifests, Helm charts, or kustomize files for the application itself
- Serverless Framework or AWS SAM configuration
- Your own Terraform, Pulumi, or CloudFormation templates
- Azure or Google Cloud deployment files

Keep these files if self-hosters use them. Deployz ignores Kubernetes, Helm, kustomize, Terraform, and Pulumi files in a deployment or sample folder, and shows a warning instead. These folders are `chart/`, `charts/`, `helm/`, `k8s/`, `kube/`, `kubernetes/`, `deploy/`, `deployment/`, `deployments/`, `infra/`, `infrastructure/`, `terraform/`, `contrib/`, `install/`, `dogfood/`, `scaletest/`, and any folder whose name ends in `-docker`. Kubernetes files still count when the application is a Go program that uses the Kubernetes API client. Files in documentation, example, and test folders are never counted.

### GPUs

Deployz runs containers on standard processors only. If your application requires a GPU, use a CPU-only configuration, or move the GPU work to a service that provides it.

## Patterns that need a repository change

Deployz can deploy these applications after you change the repository. To get instructions you can follow yourself or give to a coding agent, open **Configuration** › **Resources** and select **Get fix instructions** on the item's row. See [Fix analysis findings](/prepare/fix-findings).

### Container setup

| Detected | What to do instead |
| --- | --- |
| No Dockerfile that builds a production container image, for example one that's only for development, builds a documentation site (such as Docusaurus, MkDocs, VitePress, or Sphinx), is a template, or copies nothing from the repository | Add a production Dockerfile that builds and starts the application from source. |
| A Dockerfile that copies or reads the `.git` directory | Remove the copy or read of `.git` from the Dockerfile. Deployz builds from a source archive that has no `.git` directory. |
| A server that listens only on `127.0.0.1` or `localhost` | Bind the server to all network interfaces (`0.0.0.0`). Deployz sends traffic and health checks over the network, so a server bound to localhost never answers them. |
| A production Compose file with more than one application service | Run the application as one web service. Declare other long-running processes as workers. |
| A container image that runs several processes under a supervisor, such as s6-overlay or supervisord | Build a container image that runs only the web process, and declare each other process as a worker. |

### Local storage

The container's disk is wiped on every deploy and restart.

| Detected | What to do instead |
| --- | --- |
| A persistent volume: a Kubernetes volume claim, a Terraform-managed volume, or named volumes in a production Compose file | Store persistent data in the S3 bucket or the database. |
| A durable data or configuration directory, such as a `*_CONFIG_DIR` setting, with no `VOLUME` or Compose mount | Store the data in the S3 bucket or the database. |
| A configuration file the container image expects to be mounted, which no Dockerfile instruction creates | Create the file in the Dockerfile, or read the settings from environment variables. |
| Files written to the local disk | Store files in object storage. Deployz provides an S3 bucket for every deployment. |

### Databases

| Detected | What to do instead |
| --- | --- |
| MariaDB driver or configuration | Move to MySQL or PostgreSQL, or remove the dependency if it isn't used. |

## Platform limits

These apply to every application.

### Networking and accounts

- **Existing VPCs or databases.** Each deployment creates its own network and data services. It can't join an existing VPC or use an existing database.
- **Private connectivity.** PrivateLink, AWS Direct Connect, VPN connections, and private-only applications with no public endpoint aren't supported.
- **Custom networking.** Custom proxies, custom DNS architectures, and custom IAM aren't supported. To use your own domain, see [Add a custom domain](/operate/custom-domains).
- **Restrictive AWS accounts.** An account whose service control policies (SCPs) block the standard stack can't install. See [Before you install](/customers/before-you-install).
- **Other clouds and locations.** Deployz deploys only to AWS. On-premises and air-gapped environments aren't supported.

### Regions

- **One Region per deployment.** Multi-Region and active-active deployments aren't supported.
- **The Region is fixed.** You can't move a deployment to another Region. To use a different Region, create a new deployment. See [AWS Regions](/share/regions).

### Capacity

- **No resizing.** You can't change a deployment's size after it's created. To use a different size, create a new deployment.
- **No autoscaling.** Each web service and each worker runs one task, with the capacity of the chosen size preset. Custom AWS sizing isn't available.

See [Sizes and AWS cost](/share/sizes-and-cost).

### Changing what a deployment contains

A deployment keeps the parts it was created with. If your application later needs a database or cache the deployment doesn't have, a different database engine, or a different set of workers, queues (**Preview**), or scheduled jobs (**Preview**), Deployz refuses to deploy the new release to that deployment. To deliver it, create a new deployment for that customer, or change the application's requirements back.

These changes don't need a new deployment: dropping a database or cache the application no longer uses, changes to the runtime, and environment variable values.

Some settings apply only to new deployments:

- **Port and health check path.** An existing deployment keeps the values it was created with. To use new values for a customer, create a new deployment for them.
- **Migration command.** You can change the command an existing deployment runs on its next release deployment, or choose **No separate migration**. You can't add a command to a deployment that was created without a separate migration step. See [Database migrations](/prepare/migrations).

### Builds

- **One container image for all customers.** Deployz builds one container image per release. Per-customer builds and values that a customer enters at build time aren't supported. See [Configure environment variables](/prepare/environment-variables).

### Features that Deployz does not provide

- Deployment notifications by email or Slack, and webhooks
- Release approval workflows and scheduled releases
- Backup management beyond the database's automated backups
- Run history for scheduled jobs
- Application logs and monitoring in Deployz. Runtime logs stay in the customer's AWS account, and Deployz never copies them out.
- Actions for customers inside Deployz. Customers approve the install in their AWS console and have no Deployz account.
