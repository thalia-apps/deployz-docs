When you add an application, Deployz analyzes its repository to work out how to build, start, and host it. This page covers what to do when the analysis fails, asks you a question, or finds something you need to change. All of it happens in the Deployz dashboard, before any customer is involved.

## Analysis failed

**Symptom:** The application shows **Analysis failed**, with a reason below it.

**Checks and fixes:** Match the reason to the table.

| Reason shown | Likely cause | Fix |
| --- | --- | --- |
| No GitHub installation is linked to this application | The application isn't connected to GitHub through Deployz. | Reconnect GitHub for your organization, then re-analyze. |
| Failed to mint a GitHub installation token | Deployz lost access to GitHub, for example because the Deployz GitHub App was removed or no longer has access to the repository. | In GitHub, make sure the Deployz GitHub App is installed and can access the repository, then re-analyze. |
| Repository or branch not found | The repository or its branch was renamed, deleted, or made inaccessible. | Restore access or check the branch, then re-analyze. |
| Repository has no commits to analyze | The branch is empty. | Push a commit, then re-analyze. |
| GitHub API rate limit exceeded | GitHub temporarily limited requests. | Wait a few minutes, then re-analyze. |
| Repository analysis failed unexpectedly, or another reason | An unexpected error. | Re-analyze. If it fails again, [contact support](https://share.hsforms.com/1dOsn_DJtRhq47DXIaRjeLw5auur). |

Large repositories don't cause a failure. Deployz reads a limited set of files and skips any it can't read.

**Who acts:** you (the vendor), in the Deployz dashboard, and in GitHub if access is the cause.

## The analysis is taking longer than usual

**Symptom:** The application shows **Analyzing** with the message "Taking longer than usual. Wait, or restart the analysis." An analysis usually takes about a minute. The message appears after about two minutes.

**Fix:** Wait a little longer. If nothing changes, select **Re-analyze application** on the **Overview** card to start again. The card offers it once the message appears. The **Re-analyze application** item in **More actions** stays unavailable while an analysis is running.

**Who acts:** you.

## The result changes after a release build

**Symptom:** The **Overview** shows **Deployable with Deployz settings** with "Not yet confirmed by a build." Or the result changed to **Deployable after repository changes** with "The release build failed."

**Cause:** The analysis reads your repository without building it, so it can't predict every build failure. If release builds failed and none has passed, the result changes to **Deployable after repository changes**.

**Who:** you (the vendor), in the Deployz dashboard.

**Fix:** Select **Review failure details**, and see [Fix a failed build](/releases/build-failures). For what each analysis result means, see [Read the analysis result](/prepare/analysis#read-the-analysis-result).

## The application needs input

**Symptom:** The application shows **Needs input**. The **Overview** shows either a count of changes required before you can deploy, or **Configuration needs review**, with **Review required changes**.

**Cause:** Deployz found something it can't decide for you. The **Overview** groups the required changes into **Set in Deployz**, **Change in your repository**, and **Not supported**. For what each group means, see [Required and recommended findings](/prepare/analysis#required-and-recommended-findings).

- For items under **Set in Deployz** or **Change in your repository**, see [A finding needs a change you can make](#a-finding-needs-a-change-you-can-make). A missing start command is listed under **Set in Deployz**, but the dashboard has no start command field.
- For items under **Not supported**, see [The application needs an unsupported capability](#the-application-needs-an-unsupported-capability).

Two other kinds of input can also be open:

- **Questions about your application.** For example, which command runs a background worker. These rows are marked **Needs input** or **Blocking** on the **Configuration** screen.
- **Environment variable decisions.** A variable shows **Needs a decision** when nobody has said who provides it, or **Needs a value** when you provide it but haven't entered a value. See [Configure environment variables](/prepare/environment-variables).

**Fix:**

**Who:** you (the vendor), in the Deployz dashboard.

1. On the **Overview**, select **Review required changes**. The **Configuration** screen opens at the rows that need attention. Required items are marked **Change required**.
2. For each marked row, answer the question, edit the value, or select **Get fix instructions**.
3. Save your changes.

Open environment variable decisions block a test deployment and customer deployments. Missing build values also block release builds.

## The application needs an unsupported capability

**Symptom:** The **Overview** shows **Not deployable on Deployz** and lists one or more items under **Not supported**.

**Cause:** The application clearly needs something Deployz doesn't provide. Examples are MongoDB, SQLite as the only database, Elasticsearch, Redis features beyond a standard single-node cache, its own message broker, a GPU, or its own infrastructure code.

**Fix:** A setting can't resolve this. Change the application so it no longer needs the unsupported part, push the change, and re-analyze. For the full list and the alternatives, see [What Deployz doesn't support](/prepare/not-supported).

**Who acts:** you.

## A finding needs a change you can make

**Symptom:** The **Overview** shows a count of changes required before you can deploy, with items under **Set in Deployz** or **Change in your repository**. Or a finding on the **Configuration** screen is marked **Recommended**.

**Cause:** Deployz can host the application, but it needs a setting or a repository change first. Deployz doesn't deploy the application until you resolve every required item, including repository changes.

You resolve these in Deployz:

| Finding | How you fix it |
| --- | --- |
| Set the port your app listens on | Enter the port on the **Configuration** screen. |
| Add a health check route | Set the health check path on the **Configuration** screen. If the application has no route that returns HTTP `200`, add one first. |
| Choose how database migrations run | Choose a migration option on the **Configuration** screen. See [Database migrations](/prepare/migrations). |

You resolve these in your repository:

| Finding | How you fix it |
| --- | --- |
| Add a start command to the Dockerfile | Add a `CMD` or `ENTRYPOINT` instruction to the Dockerfile, or a `start` script to `package.json`, then re-analyze. The dashboard has no field for the start command, even though the **Overview** lists this finding under **Set in Deployz** and its suggested fix mentions the application details. |
| Add container build instructions (Dockerfile), or Has no Dockerfile that builds the app | Add a production Dockerfile that builds and starts the application from source. |
| Stop copying .git into the container build | Remove the copy or read of `.git` from the Dockerfile. Deployz builds from a source archive that has no `.git` directory. |
| Listen on all network interfaces, not only localhost | Change the application to listen on `0.0.0.0`. |
| Store files in object storage, not on the local disk, or Needs a persistent disk volume | Store files and persistent data in the S3 bucket or the database. |
| Runs as several services | Run the application as one web service, and declare other processes as workers. |
| Your database needs a supported engine (MariaDB) | Move to MySQL or PostgreSQL, or remove the dependency if it isn't used. |

When the analysis can't tell whether the application really needs an unsupported capability, for example SQLite next to a PostgreSQL driver, it lists the item under **Change in your repository**. Its fix instructions ask you or your coding agent to check first, before you change anything.

Recommended findings don't block a deployment. For examples, see [Required and recommended findings](/prepare/analysis#required-and-recommended-findings).

One recommended finding is **Background job runner**. It appears when the application seems to run background jobs, but no command starts a separate job runner. If the web process already runs the jobs, you don't need to change anything. Otherwise, declare the job runner with its own start command in your repository, for example a `worker` line in a `Procfile`, then re-analyze.

**Fix:**

**Who:** you (the vendor), in the Deployz dashboard and in your repository.

1. On the **Configuration** screen, find the finding.
2. If the fix is a setting, such as the port, health check path, or migration choice, edit it and save. You don't need to re-analyze.
3. If the fix is a repository change, select **Get fix instructions**. The **Fix deployment issues with your coding agent** dialog gives instructions you can copy into a coding agent or follow yourself.
4. Push the change to GitHub, then select **Re-analyze application**.

## A migration command is set but no database is required

**Symptom:** When you start a deployment, the **Database** check is blocked with "A migration command is set, but no database is required."

**Cause:** The application has a migration command, but the analysis found no database for it to run against. Deployz doesn't add a database to resolve the mismatch.

**Fix:** If the application doesn't use a database, open the **Configuration** screen, edit the migration command, and choose **No separate migration**. If it does use one, make sure the repository includes its PostgreSQL or MySQL driver, push the change, and re-analyze. See [Database migrations](/prepare/migrations).

**Who acts:** you.

## Re-analyze the application

**Symptom:** You pushed a change or fixed GitHub access, but the result hasn't changed. Or the application shows **Checks updated** with "Re-analyze to apply the latest checks."

**Cause:** Deployz analyzes the repository only when you add the application or start a new analysis. A push doesn't start one.

**Fix:** Re-analyze the application. For where to start it and what a new analysis keeps, see [Re-analyze the application](/prepare/analysis#re-analyze-the-application).

**Who acts:** you (the vendor), in the Deployz dashboard.
