## Read the recovery panel

When a deployment fails or needs attention, its page in the dashboard opens with a recovery panel. Read it from top to bottom:

<Frame caption="The parts of a recovery panel, shown for a failed migration.">
  <img className="dz-diagram-wide" src="/images/diagrams/recovery-panel.svg" alt="The recovery panel for a failed update, read from top to bottom. 1, what happened: Update failed, the database migration step failed, so the new version was not started. 2, impact: Release v1.3.0 is still live and unaffected. 3, cause and fix: why it happened and how to fix it. 4, recoverability: needs a change before a retry can succeed. 5, actions: Retry update. 6, Technical details, collapsed by default, with the failure code." />
  <img className="dz-diagram-narrow" src="/images/diagrams/recovery-panel-mobile.svg" alt="The recovery panel for a failed update, read from top to bottom. 1, what happened: Update failed, the database migration step failed, so the new version was not started. 2, impact: Release v1.3.0 is still live and unaffected. 3, cause and fix: why it happened and how to fix it. 4, recoverability: needs a change before a retry can succeed. 5, actions: Retry update. 6, Technical details, collapsed by default, with the failure code." />
</Frame>

1. **What happened.** The heading names the failure, such as **Install failed**, **Application couldn't start**, **Update failed**, or **Removal failed**. The sentence below it says what happened in plain language.
2. **Impact.** What still works. After a failed update, for example, the panel says that the previous release is still live and unaffected.
3. **Cause and fix.** **Why it happened** and **How to fix it**. For some failures that come from the application, Deployz writes the explanation from the failure signals instead. It then shows **Likely cause** and **Suggested fix**, and may say how sure it is. Check that kind of explanation against **Technical details** before you act on it.
4. **Recoverability.** One line that says whether the failure can clear on its own or who needs to act. The classes are below.
5. **Actions.** The recovery action, for example **Retry deployment**, **Retry update**, or **Retry removal**.
6. **Technical details.** Collapsed by default. It holds the **Failure code**, the operation and attempt, the AWS resource that failed, error messages, and, for startup failures, the container's exit code and stopped reason.

Your customer sees a simpler panel on their install page. It explains what happened, whether anything in their AWS account was cleaned up, and whether they need to act. It doesn't show the failure code.

## Who needs to act

Every failure code belongs to one recoverability class. The class tells you who needs to act, and whether retrying can help.

| Class | Line in the recovery panel | Who acts | What to do |
| --- | --- | --- | --- |
| Can be temporary | "This can be temporary. Retry when the cause clears." | You, once the cause clears | Retry when the cause clears, for example when the connector is back online. If it continues, [contact support](https://share.hsforms.com/1dOsn_DJtRhq47DXIaRjeLw5auur). On a failed first install, select **Retry deployment**. While a release is still running, there's no retry button, and the deployment recovers when the cause clears. |
| Needs a change | "Needs a change before a retry can succeed" | You, or your customer in their AWS account | Make the change the fix describes, then retry. |
| Needs Deployz | "This needs a fix on the Deployz side" | Deployz | [Contact support](https://share.hsforms.com/1dOsn_DJtRhq47DXIaRjeLw5auur). Don't retry in a loop. On a failed first install, the dashboard shows **Contact Deployz support** instead of **Retry deployment**. |
| Can't be retried as is | "Retrying will not help until the underlying requirement changes" | You | Change the requirement, for example the Region or the application itself. |

Your customer can't retry, update, or remove anything in Deployz. When the fix is in their AWS account, they make the change and tell you, and you retry.

## Contact support

[Contact support](https://share.hsforms.com/1dOsn_DJtRhq47DXIaRjeLw5auur) when:

- The recovery panel says the failure needs a fix on the Deployz side.
- You followed the fix for a failure code and the failure keeps happening.
- The failure code is `UNKNOWN` and **Technical details** doesn't explain it.

Include:

- The **Deployment ID** and the **Failure code**, from **Technical details** on the deployment page. Include the **Failure reference** if it's shown.
- The application name and the customer.
- What you were doing, and roughly when it failed, with the time zone.
- What you already tried.

Don't send passwords, secret values, or your customer's private data.
